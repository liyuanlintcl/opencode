# Omni Specs — 企业级 SDD 规范开发平台需求文档

> 本文档定义 Omni Specs 平台的全部功能性需求，覆盖从原始需求到可执行测试的完整软件开发生命周期。所有需求项均须通过后端管理平台审核后方可生效。

---

## 1. 概述

Omni Specs 是一个企业级规范驱动开发（Spec Drive Development，SDD）平台。它将传统的"需求 → 设计 → 开发 → 测试"流程标准化、结构化，并通过后端管理平台的审核机制确保每个环节的质量与可追溯性。

**核心价值：**
- 消除需求歧义：通过结构化需求 + 术语表双重校验
- 设计可追溯：每个设计模块与需求点建立多对多映射
- 变更受控：任何超出任务范围的代码修改必须重新走审批流程
- 质量可验证：验收标准自动转化为可执行测试脚本

---

## 2. 术语表（Glossary）

| 术语 | 定义 | 同义词（禁止使用） |
|------|------|-------------------|
| **需求点** | 原子级别的功能要求，不可再拆分，必须附带验收标准 | 功能点、需求项 |
| **术语表** | 本平台内所有专业术语的定义集合，用于消除歧义 | 词汇表、字典 |
| **SDD** | Spec Drive Development，规范驱动开发 | 软件设计文档 |
| **模块** | 设计文档中的功能单元，可对应一个目录或一个服务 | 组件、服务 |
| **任务** | 开发执行的最小单位，绑定到具体文件、函数、数据结构 | 工单、 ticket |
| **认领** | 开发者在开始编码前，从管理平台获取任务的独占执行权 | 领取、分配 |
| **钩子** | 在代码提交前自动执行的校验逻辑 | hook、拦截器 |
| **验收标准** | 可量化、可验证的通过条件，必须能被测试脚本覆盖 | 通过条件、checklist |
| **审批流** | 需求/设计/任务在管理平台上的多角色审核流程 | 审核、签核 |

> **规范**：本文档及平台内所有文档中，上述术语必须使用左侧精确定义，禁止使用右侧同义词。

## 3. 功能需求

### F1 需求分析 SKILL

**F1.1 需求结构化转换**
- **描述**：SKILL 接收用户的自然语言描述或原始需求文档，输出结构化的需求列表
- **输入**：纯文本、Markdown、Word 文档（可选）
- **输出**：JSON 格式的需求数组，每个需求包含：
  - `id`：全局唯一标识符（如 REQ-2024-001）
  - `parent_id`：父需求 ID（可选，用于表达需求嵌套拆分）
  - `level`：层级深度（1 表示顶层需求，2 表示子需求，以此类推）
  - `title`：需求标题（20 字以内）
  - `description`：详细描述（支持多段落）。描述中的专业术语必须使用 `[[TERM-xxx]]` 语法链接到术语表，常用连接词可不加链接
  - `priority`：P0 / P1 / P2 / P3
  - `acceptance_criteria`：数组，每个元素是一个可验证的验收标准
  - `related_terms`：数组，从 `description` 中自动解析出的术语 ID 列表
  - `source`：原始描述片段（用于追溯）
- **验收标准**：
  - [AC1-1] 任意自然语言描述输入后，输出需求数量 ≥ 1
  - [AC1-2] 每个输出的需求点必须包含至少 1 条验收标准
  - [AC1-3] 输出中引用的术语必须在术语表中存在定义，否则标记为"待补充"

**F1.2 术语表生成与维护**
- **描述**：SKILL 自动从需求描述中提取专业术语，生成术语表条目；同时支持人工增删改
- **术语表条目结构**：
  - `term_id`：唯一标识（如 TERM-001）
  - `term`：术语原文
  - `definition`：精确定义（≤ 200 字）
  - `forbidden_synonyms`：禁止使用的同义词数组
  - `scope`：适用范围（global / 特定项目）
  - `created_by`：创建者
  - `approved_by`：审批者
- **验收标准**：
  - [AC1-4] 新需求中首次出现的术语必须自动提取并进入"待审核"状态
  - [AC1-5] 术语表修改（增删改）必须触发管理平台审核流，审核通过后才生效
  - [AC1-6] 已审核通过的术语在后续需求中若被同义词替代，必须标红警告

**F1.3 需求审批流**
- **描述**：所有结构化需求必须通过管理平台的多级审批
- **审批状态**：`draft` → `pending_review` → `approved` / `rejected` → `frozen`
- **审批角色**：
  - 需求提交者（developer / PM）
  - 技术评审（tech lead）
  - 架构评审（architect）— 仅 P0/P1 需求需要
- **验收标准**：
  - [AC1-7] 处于 `draft` 状态的需求不可进入设计阶段
  - [AC1-8] `rejected` 的需求必须附带拒绝原因，打回后可修改重新提交
  - [AC1-9] `frozen` 状态的需求禁止修改，如需变更必须创建"需求变更单"走变更审批

### F2 设计方案 SKILL

**F2.1 设计文档生成**
- **描述**：基于已审批通过的需求集合，自动生成结构化设计文档
- **设计文档章节结构**：
  1. 概述与目标
  2. 需求映射矩阵（Requirement Traceability Matrix）
  3. 系统架构图
  4. 模块设计（逐个模块）
  5. 接口设计
  6. 数据模型设计
  7. 异常与边界处理
  8. 验收标准汇总
- **验收标准**：
  - [AC2-1] 设计文档必须覆盖所有 `approved` 状态的需求点，覆盖率 100%
  - [AC2-2] 每个设计模块必须明确列出对应的 `req_ids`（一个模块可对应多个需求）

**F2.2 模块级设计规范**
- **描述**：每个模块的设计必须细化到文件结构级别
- **模块设计必须包含**：
  - `module_id`：模块唯一标识（如 MOD-AUTH）
  - `module_name`：模块名称
  - `responsibility`：职责描述（单一职责）
  - `req_ids`：关联的需求 ID 数组
  - `file_structure`：文件树，示例：
    ```
    src/auth/
      ├── index.ts          # 入口，导出 Service
      ├── service.ts        # 业务逻辑
      ├── schema.ts         # 数据模型 / 类型定义
      ├── repository.ts     # 数据持久化
      └── __tests__/
          └── service.test.ts
    ```
  - `interfaces`：对外暴露的接口列表（函数签名、输入输出类型）
  - `dependencies`：依赖的其他模块 ID 数组
- **验收标准**：
  - [AC2-3] 每个模块的 `file_structure` 中，叶子节点必须是具体文件名，禁止出现模糊描述如"等"
  - [AC2-4] 模块间依赖关系不得形成循环依赖
  - [AC2-5] 接口定义必须包含参数类型、返回值类型、异常类型

**F2.3 设计审批流**
- **描述**：设计文档必须通过管理平台审核后方可进入开发阶段
- **审批关注点**：
  - 需求覆盖率（是否遗漏需求）
  - 模块拆分合理性（高内聚低耦合）
  - 接口兼容性（是否破坏现有接口）
- **验收标准**：
  - [AC2-6] `approved` 状态的设计文档必须被锁定，关联的需求自动变为 `frozen`
  - [AC2-7] 设计被拒绝时，必须明确指出哪些需求覆盖不足或模块设计不合理

### F3 任务分工 SKILL

**F3.1 任务分解与流程图生成**
- **描述**：基于已审批的设计文档，自动分解为可执行的任务列表，并生成任务依赖图
- **任务结构**：
  - `task_id`：唯一标识（如 TASK-001）
  - `title`：任务标题
  - `module_id`：所属模块
  - `req_ids`：关联的需求 ID 数组
  - `description`：详细描述（做什么、为什么）
  - `files_to_modify`：数组，精确到文件路径
  - `data_structures`：需要新增/修改的数据结构列表（含字段说明）
  - `functions`：需要新增/修改的函数列表（含签名）
  - `interface_ids`：关联的接口 ID 数组，每个任务必须绑定到设计文档中定义的至少一个接口
  - `acceptance_criteria`：任务级验收标准
  - `estimated_hours`：预估工时
  - `dependencies`：前置任务 ID 数组（为空表示可并行）
- **流程图要求**：
  - 可并行任务放在同一层级
  - 依赖关系用有向边表示
  - 关键路径高亮显示
- **验收标准**：
  - [AC3-1] 所有 `approved` 状态的模块必须被分解为至少 1 个任务
  - [AC3-2] 任务的 `files_to_modify` 必须在对应模块的 `file_structure` 范围内
  - [AC3-3] 任务依赖图必须无环

**F3.2 任务审批流**
- **描述**：任务列表必须通过管理平台审核，确认分工合理、工时评估准确
- **验收标准**：
  - [AC3-4] 处于 `approved` 状态的任务方可被开发者认领
  - [AC3-5] 任务审批时必须校验：所有依赖任务要么已 `approved`，要么已 `completed`

### F4 代码编写钩子（Hook）

**F4.1 任务认领机制**
- **描述**：开发者在开始编码前，必须在管理平台上认领（checkout）一个任务
- **认领规则**：
  - 一个任务同一时间只能被一个开发者认领
  - 认领后任务状态变为 `in_progress`
  - 开发者主动释放或超时（默认 48h 无提交）自动释放
- **验收标准**：
  - [AC4-1] 未认领任务的开发者尝试提交代码时，钩子必须拦截并返回错误
  - [AC4-2] 认领任务后，开发者本地工作区必须自动检出到对应分支（如 `feature/TASK-001`）

**F4.2 代码范围校验**
- **描述**：提交代码前，钩子校验修改范围是否超出任务授权
- **校验内容**：
  - 修改的文件必须在 `files_to_modify` 列表内
  - 新增的文件必须在对应模块的 `file_structure` 范围内
  - 禁止修改未授权的函数签名（允许修改函数体）
  - 禁止删除或重命名已授权的函数/数据结构
- **验收标准**：
  - [AC4-3] 修改了未授权文件的提交，钩子必须阻止并列出违规文件
  - [AC4-4] 修改了已授权文件但超出任务功能范围（如顺手重构其他函数），代码审查时必须标黄警告
  - [AC4-5] 如开发者认为需要修改未授权文件，必须走"需求变更单"流程，审批通过后更新任务

**F4.3 功能完成校验**
- **描述**：提交时校验是否完成了任务要求的功能
- **校验方式**：
  - 静态分析：是否调用了任务要求的函数、是否实现了任务要求的数据结构
  - 测试覆盖：新增代码的单元测试覆盖率 ≥ 80%
- **验收标准**：
  - [AC4-6] 提交信息必须包含 `TASK-xxx` 标识
  - [AC4-7] 提交信息必须包含实现逻辑简述（≥ 20 字）
  - [AC4-8] 未通过功能校验的提交必须被阻止

---

### F5 测试生成 SKILL

**F5.1 测试用例生成**
- **描述**：基于设计文档中的设计点和验收标准，自动生成测试用例
- **测试用例结构**：
  - `test_id`：唯一标识（如 TEST-001）
  - `req_id` / `task_id`：关联的需求或任务
  - `title`：测试标题
  - `type`：unit / integration / e2e
  - `precondition`：前置条件
  - `steps`：执行步骤数组
  - `expected_result`：预期结果
  - `test_data`：测试数据（可选）
- **验收标准**：
  - [AC5-1] 每个验收标准必须对应至少 1 个测试用例
  - [AC5-2] 边界条件必须被覆盖（空值、越界、最大/最小值）

**F5.2 测试脚本生成**
- **描述**：将测试用例自动转化为可执行的测试脚本代码
- **支持框架**：根据项目技术栈自动选择（如 Vitest / Jest / Pytest）
- **验收标准**：
  - [AC5-3] 生成的脚本必须能在 CI 环境中直接运行
  - [AC5-4] 测试失败时，错误信息必须能定位到对应的 `test_id` 和 `req_id`

**F5.3 测试审批与冻结**
- **描述**：测试用例和脚本需通过管理平台审核
- **验收标准**：
  - [AC5-5] 只有通过审批的测试脚本才能作为 CI 准入条件
  - [AC5-6] 需求/设计/任务发生变更时，关联的测试脚本必须自动标记为"待更新"

## 4. 非功能需求

### NF1 安全
- [NF1-1] 管理平台所有接口必须使用 HTTPS
- [NF1-2] 审批操作必须记录审计日志（who / what / when / result）
- [NF1-3] 钩子校验逻辑必须在服务端执行，禁止仅依赖客户端校验

### NF2 性能
- [NF2-1] 需求结构化转换（F1.1）单个文档处理时间 ≤ 30s
- [NF2-2] 任务依赖图渲染（F3.1）节点数 ≤ 100 时渲染时间 ≤ 2s
- [NF2-3] 代码提交钩子校验（F4）耗时 ≤ 5s

### NF3 可追溯性
- [NF3-1] 从任意一行代码提交，必须能追溯到对应的 task → design → req
- [NF3-2] 从任意一个需求变更，必须能列出所有受影响的设计、任务、测试

### NF4 兼容性
- [NF4-1] 管理平台支持主流浏览器（Chrome ≥ 100, Firefox ≥ 100, Edge ≥ 100）
- [NF4-2] 钩子支持 Git 和主流 Git 托管平台（GitHub, GitLab, Gitea）

## 5. 审批流程总览

```
原始需求
   ↓
[F1 需求分析 SKILL] → 结构化需求 + 术语表
   ↓
需求审批流 (draft → approved)
   ↓
[F2 设计方案 SKILL] → 设计文档
   ↓
设计审批流 (draft → approved)
   ↓
[F3 任务分工 SKILL] → 任务列表 + 依赖图
   ↓
任务审批流 (draft → approved)
   ↓
开发者认领任务 → [F4 代码编写钩子] 管控编码范围
   ↓
提交代码（含 TASK-xxx + 实现说明）
   ↓
[F5 测试生成 SKILL] → 测试用例 + 脚本
   ↓
测试审批流 + CI 执行
   ↓
验收通过 → merged
```

## 6. 验收标准汇总

| 编号 | 验收项 | 优先级 |
|------|--------|--------|
| AC1-1 ~ AC1-9 | 需求分析 SKILL 全部通过 | P0 |
| AC2-1 ~ AC2-7 | 设计方案 SKILL 全部通过 | P0 |
| AC3-1 ~ AC3-5 | 任务分工 SKILL 全部通过 | P0 |
| AC4-1 ~ AC4-8 | 代码编写钩子全部通过 | P0 |
| AC5-1 ~ AC5-6 | 测试生成 SKILL 全部通过 | P0 |
| NF1-1 ~ NF1-3 | 安全需求全部满足 | P0 |
| NF2-1 ~ NF2-3 | 性能需求全部满足 | P1 |
| NF3-1 ~ NF3-2 | 可追溯性需求全部满足 | P1 |
| NF4-1 ~ NF4-2 | 兼容性需求全部满足 | P2 |
